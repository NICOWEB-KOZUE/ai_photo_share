# 実装ルール

## 進め方とコード構成

- [ai_context.md](ai_context.md)の確定事項と担当機能の設計書を読んでから実装する。
- 初学者が追える小さな関数に分ける。変数・関数はsnake_case、クラスはPascalCase。コメントは日本語で理由を説明する。
- ルート名・テンプレート名・DBカラム名は設計書に合わせる。不要な抽象化や別フレームワークを追加しない。
- `app.py` のcreate_appで設定・拡張・ルートを組み立てる。モデルやフォームからapp.pyをimportしない。
- フォーム検証はforms.py、画像操作はimage_utils.py、DB定義はmodels.pyへ分ける。
- 必要なファイルだけ作成し、ユーザーの既存編集を保持する。DBや画像を初期化の都合で削除しない。

## 設定・保存先

- すべての保存先はプロジェクトルートを基準に絶対パスへ解決し、コマンド実行ディレクトリに依存させない。
- **投稿画像はプロジェクト直下の `uploads/posts/` に保存する。`static/uploads/` には置かない。** static/はCSS・JS用とする。
- DBはinstance/app.sqlite3、セッションはinstance/sessions/。両方とも公開ルートから配信しない。
- SECRET_KEYは環境変数から取得し、未設定なら分かるエラーで起動を止める。固定の秘密鍵を既定値にしない。
- 開発ではpython-dotenvを使用する。.env.exampleには変数名とダミー値だけを書く。
- .env、DB、セッション、投稿画像をGitに含めない。投稿画像は.gitignoreで除外し、uploads/posts/.gitkeepだけを追跡対象にする。

## 認証・入力・表示

- Flask-Loginでユーザー復元・ログイン・ログアウトを管理する。PeeweeのUserはUserMixinに対応させ、存在しないIDは未ログインとして扱う。remember機能は使用しない。

- ログイン状態はFlask-SessionのCacheLib方式でサーバーに保存する。ブラウザーにはセッションIDを持たせる。セッションには必要最小限のユーザーID等を保存し、パスワードは保存しない。
- ログイン成功時にセッションIDを再生成する。ログアウト時はサーバー側の状態とCookieを解除する。
- 利用によって期限を更新し、最後の利用から24時間で失効させる。期限切れをCookieだけでなくサーバー側でも判定する。
- ログイン後のHTML画面へのアクセスを利用として扱う。画像・CSS・JSの取得だけでは期限を延長しない。
- CookieはHttpOnly、SameSite=Lax。HTTPS公開時はSecureを有効にする。ローカルHTTPで動作する設定と分ける。
- 新規登録のパスワードはちょうど4文字、文字種制限なし。前後空白の除去・小文字化などで入力を変えず、Werkzeugでハッシュ化・照合する。
- usernameは前後空白を除去し、大小文字を保持。メールは前後空白を除去し小文字化。メール形式はemail-validatorで検証し、メールの所有確認や到達確認は追加しない。
- 登録・ログイン・投稿・削除・ログアウトにCSRF対策を適用する。ログイン確認と投稿の所有者確認はサーバー側で実行する。
- Jinjaのエスケープを維持し、usernameやcaptionにsafeを付けない。メール、ハッシュ、秘密鍵、詳細な内部例外を公開しない。
- リンクはurl_forを使う。POST成功後は302リダイレクト。通常の入力エラーは元フォームに表示し、パスワード・ファイル入力は埋め戻さない。

## DB操作

- User→Postの順に実装する。Likeは将来案。外部キーとユニーク制約をDB側でも有効にする。
- usernameの照合はBINARY。重複確認も同じ規則を使い、IntegrityErrorを適切な登録エラーへ変換する。
- フォームから送られた投稿者IDを信用せず、ログイン中のユーザーから設定する。
- SQL文字列へ利用者入力を連結しない。Peeweeで問い合わせ、接続はリクエスト終了・例外時にも閉じる。
- caption未入力は空文字。文字数はPythonの文字列長で確認し、DBにも140文字以下のCHECK制約を設ける。
- 日時は投稿時に生成するUTC値で保存し、表示時に日本時間へ変換する。一覧は日時降順、ID降順。
- 一覧の投稿者名は結合で取得する。投稿数に比例してユーザー取得クエリを発行しない。
- 複数のDB変更はトランザクションでまとめる。テーブル定義変更はデータ移行として扱い、既存DBの削除で済ませない。

## 画像操作

- JPEG・PNG・GIFだけを許可し、Pillowで実データを読み込んで検証する。拡張子だけでは判断しない。
- 画像ファイル自体は5×1024×1024バイト以下。フォーム全体のリクエスト上限は実装上6×1024×1024バイトとし、画像単体の検証と分ける。
- 読み込み時の過大な画素数の警告・エラーを無視せず拒否する。
- EXIFの向きに合わせて補正した後、位置情報などのメタデータを引き継がず再保存する。
- ファイル名はアプリで生成し、形式と拡張子を一致させる。元のファイル名で保存せず、既存ファイルを上書きしない。
- DBには生成ファイル名だけを保存する。画像URLは `uploaded_file` のurl_forで生成する。
- 配信はGET /uploads/posts/<filename>。投稿に紐づく生成名だけを対象とし、固定のuploads/posts/からsend_from_directoryで返す。見つからなければ404。任意のパスは受け付けない。
- DBとファイルは一括ロールバックできない。保存失敗時には作成途中の画像を片付ける。削除失敗時は成功表示せず、再処理に必要な記録を残す。

## 確認と報告

- 手動確認＋重要部分のpytestを使い、各タスクの完了条件を確認する。テストデータの保存先は実データと分離する。
- CSRF・権限・重複・入力境界・画像の異常系を優先し、単に実装をなぞるテストを増やさない。
- 依存パッケージを変更したらrequirements.txtまたは開発用依存を更新する。無関係なバージョン更新はしない。
- 完了時は変更内容、実施した確認と結果、未確認事項を報告し、tasks.mdの該当タスクを更新する。実行していないテストを成功と書かない。

既存アカウントのパスワードは変更しない。ログインでは従来の最大128文字まで受け付け、保存済みハッシュと照合する。

投稿画像の.gitignoreは `/uploads/posts/*` と `!/uploads/posts/.gitkeep` を使う。GIFは先頭フレームをPNGに再保存する。元の名前はsecure_filenameで安全化して拡張子を検証し、実際の保存名はUUIDで生成する。
